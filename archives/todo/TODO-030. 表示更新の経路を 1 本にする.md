## きっかけ

`Checker.on_mouse_up_xy()` がサーバの応答を待たずに `put_checker()` を
呼んでおり、`load_gameinfo()` の配置と別経路になっていた。共有ボードなので
**ドラッグを離した瞬間の反応は残す**（無いと操作感が悪い）。

`Position` とルール層（TODO-027）が揃ってからでないと予測が作れないので、
この一連の最後に置いた。

## やったこと

- **`Board.apply(gameinfo, {sec, history_flag, clock_state, last_op})` を
  表示を変える唯一の経路にした。** 配置・pip・バナーの更新はここにしかない
- `Board.predict_gameinfo(moves)` を足した。`this.gameinfo` を土台に、
  動かしたチェッカーの `[point, idx]` だけを書き換えて**予測**を作る。
  **`sn` は進めない。** 動かせるかは `Position.with_move()` が確かめる
- `Checker.on_mouse_up_xy()` は `put_checker()` を直接呼ぶのをやめ、
  **予測した `gameinfo` を `apply()` に渡す**
- `put_checker()` と `load_gameinfo()` は**消さずに残したが、中身は
  `apply()` へ渡すだけ**になった（既存テストが名指しで使っている）。
  **配置のロジックの二重実装は消えた**
- `tests/browser/predict.test.mjs` を足した（32 → 44 件）

### `set_turn()` が予測でメッセージを送っていた（直した）

`apply()` は `set_turn()` を呼ぶ。`set_turn()` には **`turn` が -1 以下で
勝者がいるとき `stop_clock` をサーバへ送る分岐**がある。

TODO-030 より前の `put_checker()` は `set_turn()` を呼んでいなかったので、
この分岐を通らなかった。先行実行が `apply()` を通るようになったことで、
**チェッカーを掴んでいる最中に別のタブから `turn` が -1 になると、
離した瞬間の予測で `stop_clock` が送られる**ようになっていた。

「送るメッセージを変えない」という約束に反するので、`apply()` に
「予測である」ことを渡し、**`set_turn()` の送信だけを止めた**。
表示の更新（バナーの出し入れなど）はそのまま走る。

## 残ること

- **予測は、動かした駒と dice 以外を 1 往復ぶん巻き戻す。**
  `score` / `playername` / `cube` / `turn` は `apply()` が毎回
  `gameinfo` から書き直すため。他のクライアントの変更が届いていない間だけ
  起き、サーバの返事で必ず直る。`CLAUDE.md` に書いた
- **予測が例外になると、掴んでいた駒が離した座標に浮いたまま
  サーバの返事まで残る。** ただし `with_move()` が例外を出すのは
  `gameinfo` と表示が食い違ったときだけで、両者は常に `apply()` が
  同時に作るので、今のコードでは起きない
- **チェッカーの ID と添字の変換が 3 か所に散っている**
  （`parseInt(ch.id.slice(1)) % 100`）。`Checker` 側に入口を 1 つ作ると、
  ID の作り方（`dom.js`）と対で保守できる
- `clicks.test.mjs` の「スコアの ▲ → set_score」はときどき落ちる。
  この項目より前からで、`819a7b2` でも 5 回に 1 回
