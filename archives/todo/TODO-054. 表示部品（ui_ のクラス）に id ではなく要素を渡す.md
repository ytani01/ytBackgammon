## きっかけ

TODO-049 で決めた構成の見直し（第 3 弾）の 5 つ目。表示部品が id の文字列で要素を
探し直し、チェッカーの番号も id の文字列から取り出していた（`docs/design.md` の問題 G）。

## やったこと

- **`build_dom()` が作った要素を返す**（`{checker: [[15 個], [15 個]], dice: [[4 個], [4 個]], cube, ...}`）。
  `main.js` が受け取って `new Board(els, ...)` に渡す。**`build_dom()` を呼ぶのは
  モジュールの評価時のまま**で、画像の読み込みを待ってから `Board` を作る順番は変えていない
- **`BgBase` と `ui/` のすべてのクラスが、第 1 引数で要素を受け取る。** `PlayerClock` は
  背景の要素、`PlayerName` は名前の `<input>`、`RollButton` はダイスの要素も受け取る。
  `index.html` にある要素（ヘッダ、`#board`）は今のまま id で拾う
- **チェッカーは `player` と通し番号 `num` を数値で持つ。** ID は `player * 100 + num`。
  id の文字列から番号を取り出す処理と `Board.search_checker()` を消した
- `BgBase` に `el.id` を返す `id` の getter を残した（`tests/browser/` が `ch.id` などを使う）
- テスト: `board.test.mjs` に、各表示部品の `el.id` が期待する id か照らすテストを、
  `last_op.test.mjs` に、プレーヤー 1・通し番号 10 以上の駒で put と hit の音を
  見分けるテストを足した（1 巡目の確認で、この 2 つは壊しても落ちなかったため）
- `CLAUDE.md` の `main.js`・`dom.js`・`ui/` の説明と、チェッカーの ID の段落を直した

### 見送ったこと

- **負の `ch` の `put_checker` が届くと、サーバが別のチェッカーに書き込む**（レビュー）。
  変更前からで、この項目の範囲外。範囲外の正の `ch`（999 など）はサーバで `IndexError` になり
  クライアントには届かない
- `tests/browser/predict.test.mjs` に残る `parseInt(ch.id.slice(1)) % 100` はテストのコードなので
  そのままにした

## 確かめたこと

- verifier（2 巡目）が一式を 1 回: `uv run pytest`、`ruff`、`mypy src`、`basedpyright`、
  `node --test tests/js/`、`node --test tests/browser/`。すべて通った
- `src/` に残る `getElementById` が `index.html` の要素だけで、id から番号を取り出す処理と
  `search_checker` が無いことを `git grep` で確かめた
- わざと壊して落ちること: 1 巡目の確認で put / hit の駒の引き当てを壊しても落ちず、
  2 巡目でテストを足した。実装者が 4 通り、確認担当が引き当てとプレーヤーの取り違えで
  足したテストが落ちることを確かめた
- レビュー担当が 68 か所の表示部品について、変更前に id で探していた要素と同じ要素を
  受け取っていることを実際にページを開いて確かめた。画像の読み込みの順番が変わっていないことも
  確かめたので、画像の応答を遅らせる実測はしなかった

## 残ること

- 負の `ch` の件（上の「見送ったこと」）を別の項目にするかは、利用者に聞く

## 分担の振り返り

- **各担当が見つけたこと**
  - reviewer: 動きの変わったところは無し。テストの穴 2 つの埋め方の案、負の `ch` の件、
    「キーは `Board` のフィールド名に揃え」というコメントが実際と合わないこと
  - verifier（1 巡目）: 壊しても落ちないテストの穴（put / hit の引き当て）を実装者の申告どおりと確かめた
  - implementer: テストの穴 2 つを自分で報告した
- **見込みとの食い違い:** 担当は見込みどおり。料金は $8.8 で、TODO-050〜053 の中で最も小さい。
  最初の依頼に `CLAUDE.md` を直してよいことを書いたので、そのための往復が無かった
- **次に同じ規模の項目をやるなら**
  - 「テストで押さえられていないところ」を実装者に書かせ、確認担当の壊し方をそこに向け、
    2 巡目でテストを足す流れは、3 項目続けて 1 往復で片付いた。続ける
  - 渡すものの取り違えを見るリファクタリングでは、レビュー担当に「変更前と同じものを
    受け取っているか」を全数で実測させると、要修正 0 件の根拠がはっきりする
