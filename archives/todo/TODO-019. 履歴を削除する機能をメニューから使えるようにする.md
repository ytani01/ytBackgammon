# TODO-019. 履歴を削除する機能をメニューから使えるようにする

|      | main | 担当 |
|------|------|------|
| 見込み | Opus 5 / effort high | verifier + reviewer |
| 実施 | Opus 5 / effort high | verifier + reviewer |

| 担当 | モデル | effort | output | cache_creation | 料金の割合 |
|------|--------|--------|--------|----------------|-----------|
| main | Opus 5 | high | 51,509 | 253,897 | 83% |
| reviewer | Sonnet 5 | high | 29,443 | 86,800 | 9% |
| verifier | Sonnet 5 | medium | 10,102 | 104,482 | 7% |
| 合計 |  |  | 91,054 | 445,179 | 概算 $9.0 |

- verifier と reviewer は `~/.claude/agents/` の定義のまま使い、モデルを
  上書きしていない（どちらも `model: sonnet`）。effort は定義の値
  （verifier は `medium`、reviewer は `high`）
- verifier には 2 回依頼した（実装のあとと、レビュー指摘を反映したあと）。
  2 回目は `SendMessage` で同じ担当を再開したので、1 回目の文脈を
  読み直させずに済んでいる

## きっかけ

`_history` は溜まる一方で、消す手段がサーバの再起動しか無かった。
TODO-018 では「上限を設けるのは、戻せる範囲が減るので損」として
対応しないと決めたが、**利用者が区切りたいときに自分で消せる**なら、
その心配は要らない。

## 決めたこと

- **消す範囲は「今の盤面だけ残して全部消す」。** `_history` を現在の
  `gameinfo` 1 件だけにし、`_fwd_hist` は空にする。盤面そのものは変えない
- **押した人の画面に `confirm()` を出す。** 1 枚のボードを全員で共有して
  いるので、消すと全員の履歴が消え、元に戻せない

## やったこと

- `yt_backgammon_server.py` に `clear_history()` を足した。`_fwd_hist` を
  空にし、`_history` を今の `gameinfo` 1 件だけにして `sn` を 1 に振り直し、
  `save_data()` する。盤面（`_bg._gameinfo`）は変えない
- `on_json()` に `clear_hist` の分岐を足した。**`_run_replay()` に渡す**ので、
  走っている連続再生を止めてから消す。止めずに消すと、再生の Task が
  差し替えたあとの `_history` を pop し続ける。
  `clear_history()` は待つところが無いが、`_run_replay()` へ渡すために
  `async def` にした
- `ytbg.js` に `clear_hist()` を足し、`index.html` のメニューへ
  「履歴を削除」を入れた（「連続で進める(高速)」の下、New Game の上）
- **`new_game()` にも `confirm()` を足した。** 履歴の削除だけ確認を取ると、
  同じく全員に影響する New Game との間で扱いが揃わない（reviewer の指摘）
- テストを 9 件足した（`tests/test_history.py` 4 件、`tests/test_on_json.py`
  4 件、`tests/test_clock.py` 1 件）
- `CLAUDE.md` の「履歴（戻す・進める）」に書き足した

## 確かめたこと

- `uv run pytest` 101 件、`uv run ruff check .` と `uv run mypy src` は
  指摘 0 件
- **`src/` をわざと壊して、狙ったテストが落ちることを確かめた**（7 通り）。
  `_fwd_hist` を空にしない / `sn` を振り直さない / `save_data()` を
  呼ばない / `emit_gameinfo()` しない / `_run_replay()` を通さない /
  `clear_history()` からクロックへ副作用を出す、のいずれでも、
  狙ったテストだけが落ちた
- **ブラウザで実際に触って確かめた**（Playwright で 2 枚の画面をつなぎ、
  free move を on にしてチェッカーをドラッグ）。確認は 20 項目すべて通過:
  確認ダイアログが出ること、キャンセルしたら履歴も盤面も変わらないこと、
  OK したら履歴が 1 件になり盤面は変わらないこと、もう 1 枚の画面にも
  同じように反映されること、削除後は「1つ戻す」でも戻らないこと、
  「連続で戻す」の途中で削除すると止まった時点の盤面が残って再生が
  再開しないこと、New Game でも確認ダイアログが出ること。
  確認用のサーバは利用者の 4 サーバとは別にポート 5011・`server_id` 19 で
  起動し、終わってから停止して `~/ytbg-19.json` も消した

`hist_i` / `hist_n` はサーバが送っているだけで画面には出ないので、
履歴の件数は保存ファイル（`~/ytbg-19.json`）を読んで確かめた。

## 分担の振り返り

- **reviewer が効いた。** 要修正は 0 件だったが、検討として挙げた 4 件の
  うち 3 件（`_run_replay()` の手順を書き写していること、クロックへの
  無影響を固定するテストが無いこと、`CLAUDE.md` の説明が
  「連続再生の途中で押したとき」まで届いていないこと）は main が
  見落としていた。`new_game()` に確認が無い非対称も reviewer の指摘。
  **実装が 1 ファイル 30 行程度でも、レビューの担当は省くべきでない**
- **verifier は指摘を出さなかったが、役割は果たした。** 完了条件の
  突き合わせと、わざと壊す確認をやり切っている。2 回目の依頼では
  「`_freeze_clock()` を注入しても落ちなかった（`_cur_clock()` の値を
  変えないので副作用として観測できない）」ことまで報告しており、
  壊し方の選び方を自分で判断できていた
- **見込みとは食い違わなかった**（main Opus 5 + verifier + reviewer）。
  ただし reviewer の指摘を反映したぶん、verifier への依頼が 2 巡になった
- **次に同じ規模なら**、実装とレビューの組み方はこのままでよい。
  減らせるのは main の側で、料金の 83% を占めた。内訳の大半は
  **ブラウザの実機確認**で、Playwright のスクリプトを main が書いては
  走らせて直す（チェッカーのドラッグが効く刻み幅を探る、判定の
  タイミングを直す）試行錯誤に会話が伸びた。**実機確認のスクリプト作りは
  別の担当に切り出す**と、main の会話に試行錯誤のログが積まれずに済む。
  そのときは「何を確かめるか」を依頼書に列挙し、スクリプトと結果だけを
  報告させる形にする
