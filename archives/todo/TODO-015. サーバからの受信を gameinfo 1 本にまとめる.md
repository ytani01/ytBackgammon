## きっかけ

TODO-010 で「受信側だけ一方向にする」と決めた。サーバが `gameinfo` を更新した
うえで**受け取ったメッセージをそのまま転送**し、受け取った JS が自分でもう一度
同じ操作を適用していたので、`type` の分岐がサーバの `on_json()` と
クライアントの `ws.onmessage` の**両方に同じ名前で**書かれていた。
`type` を足すときに両方直す必要があり、片方だけ直す事故が起きうる。

前提として TODO-016（クロックの状態をサーバが持つ）と
TODO-017（`load_gameinfo()` が位置の変わった駒だけ動かす）を先に済ませた。

## やったこと

### サーバ（`src/ytbg/yt_backgammon_server.py`）
- `emit_gameinfo()` に `last_op` を足した。送る `data` に
  `last_op`（受け取った msg そのまま。操作に紐づかない送信では `None`）が入る
- `on_json()` の末尾を `broadcast(msg)` から
  `emit_gameinfo(sec, history_flag=False, last_op=msg)` に変えた。
  `sec` は `put_checker` のときだけ `SEC_CHECKER_MOVE`

### クライアント（`src/ytbg/webroot/static/ytbg.js`）
- `ws.onmessage` から `gameinfo` 以外の**13 個の分岐を消した**
- `load_gameinfo()` が `last_op` を受け取り、**音と dice の回転だけ**を出す
  - `put_checker` → put / hit の音（`turn == -1` では鳴らさない）
  - `dice` → `roll` フラグによる回転と音
  - `set_turn` → turn_change の音
  - 他の 10 個に演出は無く、`gameinfo` と `clock_state` で足りる
- チェッカーのアニメーションは `last_op` に頼っていない（TODO-017 で
  `load_gameinfo()` が位置の変わった駒だけを動かすようになったため）

### テストと文書
- `tests/test_on_json.py` / `tests/test_clock.py` を、「`gameinfo` が送られ、
  その `last_op` がこの操作で、`gameinfo` のここがこう変わっている」を見る形に
  書き直した。93 件
- `CLAUDE.md` の「### 状態と通信」を書き直した

## レビューで見つかって直したもの

### 1. 勝負がついた盤面で無限ループになっていた（重大）

`load_gameinfo()` は毎回 `set_turn()` を呼ぶ。`set_turn()` の
「勝者が決まっている」枝が `player_clock[winner].emit_stop()` を送り、
サーバが `stop_clock` を処理して `emit_gameinfo()` を返すので、また
`load_gameinfo()` が走る。**`stop_clock` では `turn` も `resign` も
変わらないので、止まる条件が無い。**

| 盤面 | 5 秒間に流れた `gameinfo` |
|---|---|
| 勝ち相当（変更前の実装） | 2 通 |
| 勝ち相当（一方向化の直後） | **519〜558 通** |
| 勝ち相当（直したあと） | **0 通** |

降参だけでなく**普通に勝負がついたときも必ず踏む**。利用者と相談して
「**動いているクロックだけ止める**」を採り、`emit_stop()` を
`if (player_clock[winner].active)` で囲んだ。動いているクロックがある場合は
`start_clock` + `stop_clock` の 2 通（最大 4 通）で収束し、「勝者のクロックを
止める」役目は残る。

### 2. ドラッグ中のチェッカーが、他人のどんな操作でも定位置へ戻っていた

`load_gameinfo()` が全 30 枚を無条件に置き直すので、名前の変更でも
クロックの発着でも、掴んでいる駒が一瞬戻る（実測: `392px/292px` →
`457px/242px`）。TODO-017 では `load_gameinfo()` を通る回数が少なく目立たな
かったが、操作のたびに通るようになって表に出た。配り直しの前後で
`moving_checker` の座標と重なり順を控えて戻す形にした。

### 3. ダブルを掛けてもクロックが止まらなくなっていた

`Cube.double()` は**サーバへ知らせず自分の画面のクロックだけ** `stop()` して
いた。`cube` が `gameinfo` を返すようになったので、`clock_state` で
`resume()` され、1.5 秒後には動き出す（実測）。利用者に確かめたところ
「バックギャモンのルールに従って」とのことで、**ダブルの提示は手番の
受け渡しと同じ**（提示側が止まり、相手のクロックがテイクかパスかを
考える時間になる）ため、`change_turn()` に直した。2020 年のコミット
（`00dbf87`）では `change_turn()` を使っており、`stop()` に変わった経緯は
ファイル移動をまたぐので履歴から辿れなかった。

### 4. コメントとテストの穴
- サーバのコメント 2 か所（`broadcast` へ落ちる、転送は今までどおり）を直した
- テストの parametrize に `resume_clock` / `reset_clock` / `set_clock_switch` を足した

## 残ること

- **ブラウザでの確認は利用者が行う。** 音（put / hit / roll / turn_change）と
  dice の回転は自動テストできない。**「降参したとき」「全部上がって勝負が
  ついたとき」を必ず触ること**（いちばん重い不具合がそこにあった）。
  ダブル → テイク / パスのクロックの受け渡しも見てほしい
- **操作 1 回ごとに `gameinfo` 全体が流れる**（1 手ぶんで 700 バイト前後）。
  受け側も毎回チェッカー 30 枚の再配置と `pip_count()` ×2、`set_turn()` を走らせる。
  `emit_gameinfo()` は `broadcast()` を通るので、**操作系も「いちばん遅い
  クライアント」を待つ**（TODO-009 から続く制約。待ちの構造は変わっていないが、
  1 通が大きくなったぶん詰まりやすい）
- **クロックの表示が回線の遅い環境で 0.1 秒の単位で前後しうる**
  （`_cur_clock()` の丸めと片道の遅延）。localhost では巻き戻りは 0 回だった
- ドラッグ中の駒を**盤の外で離した**ときに `moving_checker` が残る経路がある
  （reviewer が指摘。今回の変更で作ったものではない）
- `set_turn()` の docstring は `<= -1` を「操作不可」としているが、判定は
  `== -1` のまま（変更前から）。`-2` 以下を送る経路が無いので実害は無い

## 分担の振り返り

- **reviewer が、テストでは絶対に捕まらない不具合を見つけた。** ループの
  片側がブラウザにあるので、サーバ側のテストをいくら足しても出ない。
  しかも指摘で止めず、**サーバとヘッドレス Chromium を自分で動かして
  「5 秒に 606 通、変更前は 2 通、勝者のいない `set_turn` なら 1 通」という
  対照実験まで組んだ**。引き金の特定がそれで確定した
- **implementer が「消した分岐とその行き先の対応表」を書いたのが効いた。**
  依頼で「1 つずつ書き出してから作業せよ」と指定した結果で、reviewer が
  それを突き合わせる形でレビューできた。取りこぼしはゼロだった
- **verifier は壊しテストを一貫して担い、追加テストの実効性まで確かめた。**
  一方で「JS の音の分岐は壊しても落ちない」ことも報告してきた。
  自動テストの外側がどこかを明示できるのは、確認を分けた効果
- **見込みどおり 3 担当で正しかった。** ただし**巡回は 3 回**になった
  （実装 → レビューで重大 1 件 → 修正 → 再レビューで別の副作用 1 件 → 修正）。
  受信を一方向にする変更は「送信の副作用を持つメソッドが受信経路から
  呼ばれる」形の問題を必ず作るので、**次に同種の変更をするときは、
  最初の依頼の時点で「受信処理から呼ばれるメソッドの emit を洗い出す」ことを
  実装担当の作業に入れる**
- $24.0 と、この日いちばん高い項目になった。reviewer が 37% を占めるが、
  **見つけたものの重さを考えると削れない**。減らせたのは main の 34% で、
  レビュー結果を読んで判断する往復が多かった。**判断が要る点を
  報告の先頭にまとめさせる**と、読む量を減らせる
- reviewer が 2 度セッション上限で落ちた。再開は SendMessage で続けられ、
  文脈は残っていた。**上限に当たりやすい担当には「実測より先に
  読み合わせで結論を出し、報告を書いてから余力で実測する」と指示する**のが有効
