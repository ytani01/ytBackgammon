## 2. 測り方の穴の確認

### 2-1. fsync を呼んでいない件

`grep -n "fsync\|flush" src/ytbg/yt_backgammon_server.py` は 0 件。
`save_data()` は `Path(path_name).open("w")` → `f.write(j_str)` のみで、
`os.fsync()` も呼んでいない。つまり測っているのは**ページキャッシュへの
書き込みまで**で、実ディスクへの反映（write-back）は待っていない。

これは「イベントループが止まる時間」としては**妥当**と判断する。理由:
- 実装が `fsync()` を呼んでいない以上、**本番で実際に止まるのも
  ページキャッシュへの書き込みまで**。測定はコードの実際の挙動と一致している
- ただし、これは「通常時（メモリに余裕がある状態）」の話に限る。
  ページキャッシュの dirty page が閾値を超える、あるいはメモリ不足で
  writeback 圧がかかっている状況では、バッファ書き込みの `write()`
  システムコール自体が同期的にブロックすることがあり、その場合は
  今回の測定より長く止まりうる。**この状況は今回測っていない**
  （判断できないこととして後述）

### 2-2. 文字列組み立てと write() のどちらが支配的か

`bench_breakdown.py` を新規に書き、`hist_ent2str()` によるループ組み立て
（`build`）と、`open("w")` + `write()`（`write`）を分けて測った。

```
  履歴  build中央値  write中央値  save同一F  save別F
    10     0.206ms     0.068ms   0.324ms   0.286ms
    38     0.809ms     0.126ms   0.929ms   0.898ms
   100     2.078ms     0.267ms   2.381ms   2.250ms
   300     7.585ms     0.629ms   7.577ms   7.473ms
```

**文字列組み立て（build）が支配的**。履歴 300 で build 7.585ms に対して
write は 0.629ms（全体の 1 割弱）。履歴が伸びるほど build の比率がさらに
上がる傾向（build は履歴数にほぼ線形、write は微増）。

「対処するなら `asyncio.to_thread()` へ逃がす」という TODO-004 の案は
write だけでなく build（Python のループでの文字列連結）も含めて
別スレッドへ回す必要がある。build を残したまま write だけ逃がしても
効果は 1 割弱にとどまる。

### 2-3. 同じファイルへの繰り返し書き込みで速く出ていないか

上の表の `save同一F`（毎回同じパスへ `save_data()`）と `save別F`（毎回
連番のパスへ書く）を比較。履歴 300 で 7.577ms 対 7.473ms、他の履歴数でも
差は測定誤差の範囲。**同一ファイルへの書き込みだからといって不当に
速く出てはいない**。理由は、今回の測定が `fsync()` を伴わないバッファ
書き込みのみのため、同一ファイル・別ファイルどちらでもページキャッシュへの
書き込みで完結し、ディスク I/O の実体を伴わないから（2-1 と同じ理由）。

## 4. 履歴はどこまで伸びうるか

`grep -n "_history\s*=\s*\[\]\|_history\.clear()" src/ytbg/yt_backgammon_server.py`
は、コンストラクタ内の初期化 1 箇所（53 行目）のみ。`new_game()`
（80〜108 行目）を読んだが、`_history` をクリアする行は無く、
`score` / `clock_limit` / `playername` を引き継いで `init_gameinfo()` した
あと `add_history()` を呼んでいるだけ。**つまり `_history` は
プロセスを再起動しない限り、何ゲーム続けても伸び続ける**（ゲームの
区切りでリセットされない）。

実際に手元の `~/ytbg-*.json` を確認した:

```
ytbg-1.json: history 38, fwd 0  (29KB)
ytbg-3.json: history 37, fwd 0  (28KB)
ytbg-2.json / ytbg-4.json / ytbg-9.json: history 1, fwd 0 (起動直後のまま)
```

サーバを長く動かし続けるほど、また新しいゲームを何度も始めるほど
`_history` は増え続け、1 回の `save_data()` の所要時間も比例して伸びる
（表 1〜3 から履歴数にほぼ線形）。上限が無いので、long-running な
サーバでは数百手を超えることもありうる。

## 実害についての所見（判断は利用者へ）

- 履歴 300（220KB）でも `save_data()` は 1 回あたり数 ms〜1 桁 ms 台で、
  ブラウザの操作感覚（数百 ms 単位）からすると、今の使われ方の規模
  （手元のファイルは 38 手）では体感できるほどの遅れではなさそう
- ただし `_history` に上限が無く、長時間・多ゲームで伸び続ける点、
  かつ文字列組み立てが履歴数にほぼ線形に効く点から、**将来的に
  履歴が数千手規模になれば無視できない遅れになりうる**
- 「実害があるかどうか」「対処するかどうか」は判断が要る領域であり、
  ここでは結論を出さない（管理者の指示どおり）

## 確かめられなかったこと・判断できないこと

- **メモリ逼迫下・dirty page 圧が高い状況での `write()` の遅延**は
  測っていない。今回はマシンに 4.9GiB の空きキャッシュ領域がある平常時の
  条件下での測定。`fsync()` を呼ばない実装でも、OS のページキャッシュが
  逼迫すると `write()` システムコール自体が同期的にブロックする場合が
  あり、その場合は本報告の値より大きく上振れしうる。これを再現するには
  意図的にメモリ・ディスク負荷をかける必要があり、判断できるほどの
  根拠は用意していない
- HDD など NVMe 以外のストレージでの傾向は未確認（本機は NVMe のみ）
- 複数クライアント接続時に `broadcast()` の遅い送信と `save_data()` の
  ブロックが重なった場合の複合的な影響（TODO-009 の broadcast の話との
  相互作用）は、今回は測っていない（`FakeClient.send_json()` を
  ほぼゼロコストにしているため）
